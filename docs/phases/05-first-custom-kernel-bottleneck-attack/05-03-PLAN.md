# Plan 05-03: Custom gfx1100 GEMM Kernel with Hardware WMMA for Prefill ($M \gg 1$)

**Phase:** 5 - First Custom Kernel (Bottleneck Attack)
**Goal:** Author and optimize the custom gfx1100 GEMM kernel using RDNA3 hardware matrix cores (`__builtin_amdgcn_wmma_f32_16x16x16_f16_w32`) for batched prompt prefill ($M \in [16, 2048]$).
**Requirement:** KERN-02, KERN-03 (Prefill aspect)
**Depends on:** 05-01 (Reference & comparator harness)

## Deliverables
1. `kernels/matmul_iq4xs/impl_gemm_wmma.hip` — Custom fused IQ4_XS GEMM kernel using RDNA3 WMMA hardware intrinsics:
   - $16 \times 16 \times 16$ tile matrix multiply-accumulate on Wave32 (`__builtin_amdgcn_wmma_f32_16x16x16_f16_w32`).
   - On-the-fly register dequantization of `block_iq4_xs` into packed FP16 input fragment registers.
   - Padded LDS allocation `[32][33]` (132 bytes per row) to eliminate 32-way LDS bank conflict stalls.
   - Double-buffered shared memory pipeline overlapping global memory fetching with matrix core computation.
2. `kernels/matmul_iq4xs/test_gemm_compare.cpp` — Standalone numerical validation harness comparing against CPU oracle across $M \in \{16, 128, 512, 2048\}$ asserting $\text{cosine} \ge 0.999$.
3. `kernels/matmul_iq4xs/bench_gemm.cpp` — Dedicated GEMM microbenchmark sweep measuring TFLOP/s and latency across batch sizes $M \in \{16, 64, 128, 256, 512, 1024, 2048\}$ against stock `llama.cpp` HIP and Vulkan.

## Technical Strategy

### 1. WMMA Matrix Fragment Mapping
* Each Wave32 wavefront processes a $16 \times 16$ output tile of $C$:
  ```cpp
  typedef float  v8f32 __attribute__((ext_vector_type(8)));
  typedef _Float16 v8f16 __attribute__((ext_vector_type(8)));

  v8f32 c_frag = {0.0f}; // Accumulator

  for (int k_tile = 0; k_tile < K; k_tile += 16) {
      v8f16 a_frag; // 16x16 FP16 tile from Weight matrix W (dequantized on-the-fly)
      v8f16 b_frag; // 16x16 FP16 tile from Activation matrix X (loaded from LDS)

      c_frag = __builtin_amdgcn_wmma_f32_16x16x16_f16_w32(a_frag, b_frag, c_frag);
  }
  ```

### 2. LDS Tiling & Bank Conflict Elimination
* Threadblock shape: $64 \times 64$ output tile computed by 16 Wave32 wavefronts (512 threads per block, or $64 \times 32$ computed by 8 wavefronts / 256 threads).
* Activation matrix $X$ is loaded into shared memory buffer $B_{\text{lds}}$:
  - Declared with stride padding: `__shared__ half B_lds[2][16][64 + 2];` (double buffered, padded by 2 halfs = 4 bytes).
  - Guarantees zero bank conflicts when 16 threads in a wave read columns simultaneously.
